# Extension Release

## 0. Project Configuration

Read these from `CLAUDE.md`; ask once for anything missing and offer to record it.

| Key | What it is |
| --- | --- |
| **Project name** · **Audience · client** | Which product and client this repo is. |
| **Browsers** · **Extension ids** · **Store listings** | Which stores the release goes to, under which ids and listings. |
| **Single purpose** · **Target sites** · **Surfaces** | What the listing must say, and which pages and surfaces the browser check must walk. |
| **Release owners** | Who may run the production deploy. |
| **Production status** | Not published yet (the first release, Section 6) / published. |
| **Sign-in providers** · **Payments** · **Analytics** | Decide which flows the browser check walks and which disclosures the stores need. |
| **Backend repo path** · **Production API URL** | To confirm the backend the release depends on is live. |
| **E2E command** | Playwright, for the smoke suite and the screenshots. |
| **Crash-free floor** | The rate below which the rollout halts; 99.5% unless `CLAUDE.md` says otherwise. |

## 1. Scope

`ci-cd`'s pipelines build, zip, smoke-test, submit and tag. A release needs more than a pipeline can do: a version worth releasing, honest release notes, listings and disclosures that match the code, a person's check in real browsers, a review by each store, a rollout watched by someone who can halt it, and a record. This skill does those, in order, and stops for my approval at every point where something becomes public.

There is one kind of release. Every change — a feature, a fix, a dependency bump — reaches users as a new version through the stores' review, and nothing reaches them any other way. The only choice is **where the commit comes from**:

- **A release from `main`** — the normal case: `staging-current`, verified on staging, carrying everything merged since the last release.
- **A hotfix** — a fix for the live version that cannot wait for the unreleased work on `main`: the `hotfix/vX.Y.Z` branch from `ci-cd` → Hotfixes, carrying one fix and a patch bump, verified by its own staging run, submitted by SHA. The manual checklist is reduced to the flows the fix touched. It still waits for review; nothing skips that.

Building features is `/extension-build`'s work, fixing bugs `/extension-issue-fix`'s. This skill changes no product code; a problem it finds goes to those skills first.

## 2. Reference — Governing Files

| File | What it is |
| --- | --- |
| The UI tracker and the staging deploy message | What is `Integrated` since the last release, and the commit on staging. |
| `docs/release/listing.md` | The listing per store: name, summary, description, category, the single-purpose statement, support and privacy URLs, the languages. Written on the first release, updated when the product changes. Each store's length limits noted beside its field. |
| `docs/release/permissions.md` | Every permission, host permission and optional permission, with the feature that needs it and the justification filed with each store, in the words the stores read. Changes only with a change to `wxt.config.ts`. |
| `docs/release/privacy.md` | What the extension collects, reads from pages, stores and transmits, and why — the answers to the Chrome Web Store privacy practices form, the Firefox `data_collection_permissions` declaration, the Edge privacy disclosures, and the privacy policy on the product's web domain, all saying the same thing — and the code each answer rests on. |
| `docs/release/checklist.md` | The release checklist this skill runs, extended whenever a review catches something. |
| `docs/release/screenshots/` | The current screenshots per store and size, generated by Playwright, and the spec that produces them. |
| `docs/release/releases/vX.Y.Z.md` | One record per release: the commit and backend commit, what changed, the browser check, each store's review outcome and time, the rollout timeline, incidents, and what the next release should learn. A hotfix is a release and gets its own record. |
| `docs/infra/infra-setup.md` | The store accounts, the ids, the credentials; the steps only I can do. |
| Sentry, the store dashboards | Error rates per version and browser, review status, the rollout percentage, user reviews and ratings. |

**Standards**: `ci-cd` for the pipelines, tags and rollback; `security` → Store compliance for what the listings and disclosures must be true to, and → Permissions for what may be asked; `testing` → Browser matrix for where the check runs; `DESIGN.md` → Content and Voice for the release notes and the listing. Follow them as written.

## 3. Constraints

- **Nothing becomes public without my approval**: not the production deploy, not a listing change, not a rollout step. Running the production deploy is the first approval; publishing after review where a store defers it, and each rollout raise, are more.
- **A release is checked in real browsers** against the production backend before its rollout is raised past the pipeline's first step. A runner is not a browser: the install prompt, the toolbar, the side panel chrome and the real target sites only show in one.
- **The backend goes first.** A release that needs backend changes waits until the production backend is live with them, and the record names that commit.
- **The listings and disclosures match the package that is submitted.** Reviews are rejected for mismatches more often than for bugs: a permission with no justification, a disclosure that misses something the code sends, a screenshot of a screen that does not exist, a description that promises more than the single purpose, a privacy policy URL that does not resolve. The checklist exists for this.
- **Release notes are true and in the product's voice.** What the user will notice, from the tracker; never "bug fixes and improvements" when there is something to say. They name the backend commit the release was verified against. A target site whose anchors changed is named.
- **A new permission is its own release.** It disables the extension for Chromium users until they accept it, so it ships with the feature that needs it, explained in the release notes and the listing, never alongside a fix users need.
- **Rollouts are gradual where a store allows it, and watched everywhere.** The Chrome Web Store offers a percentage rollout only for items above its active-user threshold; Firefox and Edge publish to everyone at once. No release goes to 100% on Chrome without the crash-free rate holding at each step. A halt is not a rollback: `ci-cd` → Rollback says what each store can undo — Chrome and Firefox republish the previous version under a new, higher number; Edge only fixes forward.
- **All stores release together** from one pipeline run. Reviews finish at different times; a store that is late by more than a few days is a decision for me, not a reason to hold the others silently.
- **Review findings are never argued around.** A reviewer's objection is classified (Step 5) and either fixed or raised with me; the package is never changed to behave differently for the reviewer.

## 4. Workflow

### Step 1 — Decide the release → **wait for my approval**

1. `pnpm docs:pull`, commit what it changed. Read the tracker for everything `Integrated` since the last `v*` tag, and the staging deploy message for `staging-current` and its version.
2. Confirm the staging checklist passed on the browser matrix — including an update over the previous staging build — and the Playwright suite is green on `staging-current`. If not, stop: there is nothing to release.
3. Confirm every backend change the release depends on is live in production, and that every deprecation the backend's handoff listed is adopted in this commit.
4. Diff the manifest since the last release: a new permission, host or optional permission, a changed CSP, a changed `data_collection_permissions`. Each is a release decision and a disclosure change, called out here.
5. Present: **from `main` or a hotfix**, and why; the changes, grouped by feature area, in user terms; the units built but not yet integrated, which stay unreachable in production and out of the release notes; the manifest changes and what each means for users and for the disclosures; the proposed version (semver: patch for fixes, minor for features, major for a restructure — every release needs a higher number, in the three-part form the stores accept); the backend commit it depends on; anything in Section 3 that is not yet true.

### Step 2 — Prepare

1. **Version:** a PR that bumps `package.json` to the approved version — the pipeline never bumps it, so the release stays reproducible from its commit. For a hotfix the bump is on the hotfix branch. Give me the link; the release continues from the merged commit, which Pipeline 2 verifies on staging again.
2. **Release notes:** the "what's new" text, from the changes, in `DESIGN.md`'s voice, with the backend commit, under each store's length limit. They go in the release record, in each store's version notes, and — where the product shows notes in its update banner — there too.
3. **Listing:** if the product's surfaces, name, description, category or screenshots changed, update `docs/release/listing.md` and say what changed, per store.
4. **Permissions:** if the manifest changed, update `docs/release/permissions.md` — a justification for each new permission, in the words the Chrome Web Store's per-permission field asks for — and present it.
5. **Privacy:** diff `docs/release/privacy.md` against the code since the last release — new data sent, new page data read, a new SDK, analytics turned on, a new storage item — and update the Chrome privacy practices answers, the Firefox declaration in `wxt.config.ts`, the Edge disclosures and the privacy policy page to match, listing every change for me. The four must say the same thing.
6. **Screenshots:** if any screen in the current set changed, regenerate the set with the Playwright screenshot spec, at the sizes each store currently requires (check their documentation; the sizes change), on production-like seed data, showing the surfaces and content UI the listing describes. **Look at every screenshot.** Replace the set in `docs/release/screenshots/`.
7. **Review account:** confirm the reviewers' account on the production backend exists, signs in with email and password, and can reach every feature behind sign-in; note anything a reviewer could not reach (a paid feature, a role-gated screen, content UI on a site that needs an account) and how the review notes explain it, with a fixture page URL where a target site cannot be shown.
8. **Checklist:** run `docs/release/checklist.md` and present what passed and what did not.

### Step 3 — Build and submit

Run the production deploy (`ci-cd` → Pipeline 3) with the commit's SHA, or ask me to if I am the release owner. It checks the version against the last `v*` tag, builds every target, zips them (and the Firefox sources zip), runs the smoke suite on the Chromium build, and — only if it passes — submits to the Chrome Web Store, Firefox Add-ons and Edge Add-ons and tags `vX.Y.Z`. A failed smoke run stops here, nothing was submitted, and the failure goes to `/extension-issue-fix`.

Before the run, where the Chrome item is eligible for a percentage rollout, set the percentage to the first step (10%) so the publish after review opens at that step; otherwise the publish is to 100% and the browser check (Step 4) is the only gate before users, so it runs on the staging build **before** this step as well. Where Safari is on, build the `safari-mv3` target, run Apple's packager on a Mac, and submit through App Store Connect as `docs/release/checklist.md` describes.

### Step 4 — Browser check → **wait for my approval**

Only a person can install a build in a real browser and open the real target sites, so this check is mine: you give me the checklist below per browser, I run it against the production backend with the review account, and report what I saw; you record it and present it. What I run it on differs by store, because Firefox publishes on signing and Edge on certification: the Chrome check runs on the production zip from the pipeline's artifacts, loaded unpacked, while Chrome's publish is deferred; the Firefox and Edge checks run **before Step 3**, on the staging builds (the staging Edge zip loaded unpacked, the staging `.xpi`) and on the production Firefox build through `web-ext run`, whose temporary install with the production `gecko.id` gives the same redirect URL — and again on the published versions once they are live, which is also where the update-over-previous check for those two browsers runs.

- **A fresh install** in each: the install prompt lists exactly the permissions and, on Firefox, the data declaration the listing describes; the toolbar icon, the popup, the side panel and the options page open; nothing asks for a permission the listing did not mention.
- **An update** over the previous production version in each: the session survives, preferences survive, no new permission prompt unless the release added one.
- The staging checklist's flows, read-only where they would create real data; sign-in with email and password and with each provider through the identity flow; the checkout return where payments are on; a context-menu entry and a command opening the right surface; content UI on each target site's real page, in the states the flows define; the options page saving a preference.
- The force-update screen, by pointing a build at a test minimum version if the backend offers one.
- Light and dark following the browser theme; 100% and 200% zoom; the popup at its minimum and maximum height; the browser restarted mid-session; the network cut mid-flow; the extension disabled and re-enabled.

**Present the check in the chat** from my report, browser by browser, and end with anything that failed. A failure withdraws whatever a store still holds (Chrome's deferred publish, Edge in certification — `ci-cd` → Rollback); a store that already published is rolled back where it can be (Chrome, Firefox) or fixed forward (Edge); the fix goes to `/extension-issue-fix`, and the release starts again from Step 1 as a hotfix.

### Step 5 — Review outcomes

Each store reviews on its own timeline — the Chrome Web Store usually within days, Firefox Add-ons often within hours for a listed update with sources, Edge Add-ons up to a week. Follow each in its dashboard.

- **Approved:** on the Chrome Web Store, where publishing is deferred, publish on my word at the rollout step set in Step 3; Firefox and Edge publish on approval. Record the time. When every store has published, go to Step 6.
- **Approved on some, pending on others** past a few days: ask whether to hold or publish what is approved. Say what a split publish means: users of one browser on the new backend contract before the others, which the backend's additive-only rule makes safe.
- **Rejected or flagged:** read the finding in full and classify it — a **metadata problem** (a justification, a disclosure, a screenshot, a description) is fixed in `docs/release/` and the store's form and resubmitted; a **bug** goes to `/extension-issue-fix` and the release restarts from Step 1; a **policy question** (a permission the store disputes, a data use, the single purpose read differently) is presented to me with the options and the store's text, and nothing is argued with the reviewer until I decide. A takedown or a warning on the published item is an incident: tell me at once, because the next version then has to go to 100% and the account's standing is at stake. Every finding and its resolution is recorded, and the checklist gains a line so it does not happen twice.

### Step 6 — Roll out and monitor

1. Watch Sentry's crash-free sessions and new issues for the new version, per browser, the backend's error rate for the new `X-App-Version`, the stores' ratings and reviews, and the adoption each store's dashboard shows, at each step: after the first hour, the first day, and before each raise.
2. **Raise the Chrome rollout** — 10% → 25% → 50% → 100%, each step on my word, over days not hours, from the dashboard's rollout field (raising it needs no new review) — only while crash-free sessions hold above the floor in every browser and no new issue affects a critical flow. Firefox and Edge are already at 100%, so their first day is watched the closest.
3. **Halt** the moment an error or a critical issue spikes in any browser: hold the Chrome percentage where it is, or roll back on Chrome and Firefox (each republishes the previous version under a new, higher number you give it; note the numbers in the release record, because the next release must exceed them), tell me, and route the fix through `/extension-issue-fix` as a hotfix. A halted release is recorded with what happened; the Chrome rollout is never resumed with the same version — the fix ships as the next one.
4. At 100% everywhere: tell the backend the release is published with its version per browser, so it can plan the minimum-version change; update `CLAUDE.md`'s production status; close the release record with the timeline, the review times and what the next release should learn.

### Step 7 — Report

The version, from `main` or a hotfix; what shipped, by feature area; the manifest changes; the browser check; each store's review outcome and time; the rollout timeline and the crash-free rate per browser at each step; incidents, if any; the backend commit the release runs against; and anything to carry into the next release. Commit `docs/release/` and deliver it as a PR: branch off `origin/main`, push, give me the link. Never create the PR yourself.

## 5. Safari

Off by default, because it needs a native app wrapper, Apple's signing and App Store review, and a Mac to build on. Where `CLAUDE.md` turns it on:

- Pipeline 3 produces the `safari-mv3` build; on a Mac, `xcrun safari-web-extension-packager` wraps it in the Xcode project the infra guide records, which is signed with the Developer ID and submitted through App Store Connect with its own listing, screenshots and privacy answers.
- The Safari build is checked on the browser matrix like the others; its review is followed like the others' (Step 5), and its record is a line in the release record.
- Check Apple's current requirements for Safari web extensions at the time, not from memory; they change.

## 6. The First Release

Before Step 1 can run the first time:

1. **The store accounts and ids exist** per the infra guide: the Chrome Web Store developer account (and its publication limit, two items by default), the Firefox Add-ons account, the Edge Partner Center account, and the Apple Developer Program where Safari is on. The production Chromium ids are assigned by the first upload to each store: upload the first production Chrome zip to the Chrome Web Store as a draft and the Edge zip to Partner Center, record both ids — and the Chrome item's public `key` from its Package tab — in `wxt.config.ts` and `CLAUDE.md`, register both identity redirect URLs with the production backend, and rebuild before the first real submission, so sign-in works in the published extension. The production `gecko.id` is yours to choose and is registered the same way.
2. **The listing is written from scratch** in `docs/release/listing.md` from the product brief and the design system's voice: the name, the summary and description per store's limits, the category, the single-purpose statement that every permission must serve, the support URL and privacy policy URL on the product's web domain (both required and both must resolve). Present it for approval.
3. **`permissions.md` is written** from `wxt.config.ts`: every permission, host and optional permission with the feature that needs it and its justification. Present it for approval; a permission no feature can justify is removed from the manifest before the first submission, not explained around.
4. **`privacy.md` is written** from the code: every kind of data collected, read from pages, stored and transmitted, the Chrome privacy practices answers, the Firefox `data_collection_permissions` declaration, the Edge disclosures, and the privacy policy page, all saying the same thing. Present it for approval.
5. **The screenshot spec is written** in Playwright, on seeded data and the fixture pages, producing the sizes each store requires, and run; every screenshot looked at.
6. **The review account** is created on the production backend with the backend developer, and the review notes drafted — how to sign in, how to reach each gated feature, which target site shows the content UI and a fixture page URL where the site needs an account.
7. **The checklist** is written from Sections 3 and 4 and the three stores' current program policies and review guidelines, read at this moment, not from memory.
8. **The backend is told before the first submission.** The Backend Blueprint is installed with `--store-client`, so its deprecations register exists, and the backend developer sets `Client release status` in the backend's `CLAUDE.md` to shipped: from then on every breaking change takes its deprecation path, and the minimum version for `X-Platform: extension-chrome`, `extension-firefox` and `extension-edge` (and `extension-safari`) rises only to versions every store has published — which is why Edge is its own build: one zip for both Chromium stores could never report `extension-edge`.

Then Steps 1 to 7 as above. The first Chrome release is not eligible for a percentage rollout (the item has no users yet), so the browser check runs on the staging build before Step 3 and again on the production zips before publishing; the first week is watched the closest.

## 7. Definition of Done

- [ ] The release was decided on the tracker and the staging verification, with the backend's production commit confirmed live and every manifest change called out.
- [ ] The version was bumped by a PR; the release notes, listing, permission justifications, privacy disclosures and screenshots match the submitted package; the checklist ran.
- [ ] The build was checked in every target browser against the production backend — fresh install and update, the real target sites — and the check was presented.
- [ ] Every store's review outcome, findings and their resolutions are recorded.
- [ ] The release reached 100% in every store with the crash-free floor holding, or was halted and recorded.
- [ ] The backend was told the version is published; `CLAUDE.md` and the release record are updated; the PR link was given.
