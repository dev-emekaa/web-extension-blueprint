# Extension Setup

Builds the foundation every screen stands on. It runs once per project, before the first `/extension-build`. It needs no product docs and no design system, so it can run while those are being written — only the design tokens step waits for `DESIGN.md`, and it can be run again later for that step alone.

It builds no screens: not even sign-in, which is a feature area designed and built from its own docs. It adds only what every extension needs. A library or a permission only some features use (data tables, `downloads`, `offscreen`, `declarativeNetRequest`, a host permission for one site) is added by the first build that needs it.

## Read first

- **The rules in `.claude/rules/`:** `tech-stack`, `coding-standards`, `security`, `testing` and `ci-cd` (and `analytics` where installed). They define what this skill builds, and it does not restate them.
- **`CLAUDE.md`:** the audiences and clients, which audience this repo serves, and the project configuration. If the backend repo path, the single purpose, the target sites or the staging API URL is not recorded, ask once — the single purpose and the target sites decide the permissions, and the permissions decide what the stores will accept.
- **The backend's `docs/api-docs/`** if any exist yet, for the auth endpoints' exact paths and the platform and version headers. Until they do, the auth paths are constants in `background/session/paths.ts`, set to the backend's conventional paths and corrected when the auth area is integrated; the headers are set in `background/gateway/fetch.ts`.

If the repository already has code, take stock first. Keep what meets the rules, add only what is missing, and list anything that conflicts with the rules for me to decide. Never rebuild working pieces unasked. A Manifest V2 package, remote code, `<all_urls>` without a reason, a token readable from a content script, or `externally_connectable` open to the web is the first thing to raise: the security rule does not bend for existing code.

## Step 1 — Plan → **wait for my approval**

State what exists, what will be created, and anything the rules leave to this project: the browsers, the surfaces the product has, the permissions the single purpose needs (install-time, optional, and host — each with the justification the stores will read), the target sites and their match patterns, which sign-in providers (and, if Safari is on, which sign-in path it gets, since Safari has no `identity` API), whether the product has a context-menu entry, keyboard commands or an omnibox keyword. Check the current stable version of WXT and each tool in `tech-stack` rather than relying on memory — WXT is pre-1.0 and a minor bump is a breaking one — and say which versions the scaffold will use. Check the current names of the settings and options the rules name (pnpm's supply-chain settings, WXT's manifest and zip options, `wxt submit`'s flags, the stores' manifest requirements such as Firefox's `data_collection_permissions`) against each tool's current docs: they change.

The permission list is the decision that matters most in this plan. A permission added later disables the extension on Chromium until the user accepts it, and every one widens the store review; a permission left out is a feature that asks at the moment of need. Recommend the narrowest set and say what each one costs.

## Step 2 — Scaffold the extension

- **The project per `tech-stack`:** WXT with the React module and TypeScript strict in three `tsconfig` projects, Tailwind, ESLint and Prettier configured as `coding-standards` says, a pre-commit hook running lint-staged, pnpm with its settings in `pnpm-workspace.yaml` (the supply-chain ones `security` requires), `web-ext` for the Firefox lint and run.
- **`wxt.config.ts` keyed by `APP_ENV`:** the name with its `Dev` and `Staging` suffixes, the icon variants, the fixed ids (a generated `key` for the Chromium dev and staging builds, `browser_specific_settings.gecko.id` for Firefox — chosen, not assigned — and, once known, the production `key` the Chrome Web Store's id derives from; the Edge build carries no `key`, since Edge Add-ons assigns its own id), the `edge-mv3` target beside `chrome-mv3`, `data_collection_permissions` with `technicalAndInteraction` optional in every build (Sentry ships in every build), the permissions and host permissions from the plan with a justification comment on each, the optional permissions, the extension pages' CSP per environment, the commands from `shared/shortcuts.ts`, the side panel (`side_panel` on Chromium, `sidebar_action` on Firefox) and the options page, and the `background` entry WXT emits per target. It throws on a production build with `API_MODE=mock`, and on a production build whose API URL is not the production one.
- **`.env`, `.env.staging`, `.env.production`** with the environment's constants (API URL, Sentry DSN, mode), declared and validated in `src/shared/env.ts`.
- **The entrypoints** from `coding-standards` → Project structure: `background.ts` registering the modules, `popup/`, `sidepanel/`, `options/` and `app/` each mounting a surface app with its own router and query client, and one example content script (`example.content.ts`) matching the fixture page only. `src/shared/` with the protocol, the environment and the shared types.
- **The messaging protocol** in `src/shared/messages.ts`: every message `coding-standards` names, each with its Zod payload and result schemas and the contexts allowed to send it; `background/messaging.ts` registering handlers with payload parsing and sender validation (`security` → The background is the trust boundary); `lib/messaging.ts` building the typed client; `lib/api.ts` typing `api:fetch` for the surfaces.
- **The surface shell** in `components/shared/`: the header with the account entry, the signed-out state with the sign-in prompt, the permission-needed state, the empty, error and offline states, the update banner, and a loading skeleton. The shell is only a placeholder here (a header and a content area at the popup's width); its form is decided by `/design-system` and it is designed and built in `/extension-build`'s Phase 0.
- **shadcn/ui initialised** with the base components every product needs: button, input, label, form, select, checkbox, switch, textarea, dialog, sheet, dropdown menu, popover, tooltip, toast (sonner), tabs, card, badge, avatar, skeleton, separator, scroll area, command. More are added per build.
- **The routers**: `createMemoryRouter` per surface with the signed-in and signed-out trees, each with a layout and an error boundary, a not-found route, the session guard from `useSession`, the readiness guard for un-integrated units, and the initial route from `?route=`. Routes are placeholders that the builds replace.
- **Fonts** as `DESIGN.md` will name them: the system stack now, bundled files under `public/fonts/` later; the theme following `prefers-color-scheme`, wired for dark mode in the surfaces and inside shadow roots.

## Step 3 — Session, gateway and data layer

Exactly as `coding-standards` → sections 3 to 5 describe:

- `background/session/`: the access token in `storage.session`, the refresh token in `storage.local`, the `navigator.locks` single-flight refresh, the wake behaviour, the identity flow (`launchWebAuthFlow` to the backend's sign-in URL with PKCE and `state`, the redirect URL from `identity.getRedirectURL()`, the code exchange; on Safari, the tab-based flow the plan chose, watching `tabs.onUpdated` for the `https` return page), email-and-password sign-in through the gateway, sign-out with the clearing order `coding-standards` gives, and the `session:changed` broadcast.
- `background/gateway/core.ts` with `ApiError`, the status table, and the base URL that mock mode points at the in-process dispatch; `background/gateway/fetch.ts` with the bearer header, `credentials: 'omit'`, the platform header from the build target and the version header from the manifest, single-flight refresh-and-retry, and the offline mapping; `background/gateway/realtime.ts` with the port-held stream — a WebSocket authenticated by the Socket.IO `auth` payload or a single-use ticket, or SSE over `fetch` with a heartbeat — as `coding-standards` → Messaging and the gateway says.
- `lib/api.ts` rebuilding `ApiError` from messaging, and `lib/query-client.ts` with `createQueryClient(surface)`: the defaults (`staleTime`, retry rules), the `storage.session` persister keyed by user id, `onlineManager` from `navigator.onLine` and the gateway's offline events, `focusManager` for the side panel and options page.
- `hooks/use-me.ts`, `hooks/use-session.ts`, `hooks/use-online.ts`, `hooks/use-version-state.ts` with its `supported` / `soft` / `force` states and the placeholder screens for the last two, `hooks/use-permission.ts`, `hooks/use-shortcut.ts` reading the live bindings.
- `pnpm api:types`, generating `src/shared/api.ts` from the backend's OpenAPI spec recorded in `CLAUDE.md`. The backend exposes one only once it is built, so the script is wired here and first run at the first integration; until then every feature's types are provisional, per `coding-standards` → Messaging and the gateway.
- **Local dev against a deployed backend:** a `pnpm dev:staging` script that runs `wxt dev` with the API URL pointed at staging in direct mode. The API origin is a host permission, so no CORS work is needed.

## Step 4 — Mock mode

The semantics — the mode switch, in-process dispatch in the background, passthrough, sessions, the sign-in-first rule, the production exclusion, the readiness gate — live in `coding-standards` → Mock mode and are not restated here. This step creates the pieces:

- The dispatch in the gateway's `core` behind `API_MODE`, importing the mock module only outside production.
- The handler helper: `defineHandlers({ 'GET /clips': ({ query, session }) => ... })`, with path parameters, latency simulation, state in `storage.session` (so a created record survives the worker's restart), and the `?mock=error` switch — plain functions with no `browser` imports, so the surfaces' test double runs them too.
- `background/mocks/auth.ts`, the mock auth for the conventional auth paths (`/auth/sign-in`, `/auth/sign-out`, `/auth/refresh`, `/auth/me` — corrected at integration), returning JWT-shaped tokens through `session`. In mock mode the identity flow is skipped: the sign-in prompt's provider buttons call the mock sign-in directly, and say so in a development-only label.
- `src/test/api-double.ts`, the messaging double over the same handlers for Vitest.
- One example feature folder, `features/_example/`, showing provisional types, a query hook, a virtualised infinite list, a mutation hook, fixtures, handlers, a popup screen with every state, a side-panel screen, a form on the full-tab page, and content UI mounted on the fixture page, deleted by the first real build.

## Step 5 — Design tokens *(when `DESIGN.md` exists; otherwise placeholders, and re-run this step later)*

- `styles/globals.css` defining `DESIGN.md`'s colors, radii, spacing and type scale as CSS variables under the shadcn names — each color in `:root`, its `-dark` twin under `.dark` — the shadows from its Elevation & Depth table, and the popup width, the side panel's minimum and the content maximum from its Layout section, all exposed to Tailwind.
- `styles/content.css` with the same tokens in pixels and the `:host` reset, for the shadow roots, and the content build of Tailwind with a pixel root.
- The shadcn components adjusted to the design system's radii, borders, focus rings and type.
- The fonts `DESIGN.md` names, bundled, with the `web_accessible_resources` entry content UI needs for them, restricted to the target sites.
- The durations and easings from its Motion table as CSS variables, and a `lib/motion.ts` exporting them for Motion.

## Step 6 — Browser layer

Wired once, used by the builds:

- **Content-script mount:** `content/mount.ts` with `createShadowRootUi`, the tokens and styles injected, `Portal` containers, idempotent mounting, and cleanup on `ctx.onInvalidated`; `content/anchors.ts` with the debounced, scoped `MutationObserver`; `content/page.ts` with the validated selection and anchor-text readers.
- **Permissions:** the optional-permission request flow — the surface calls `browser.permissions.request` in its own click handler after the explanation sentence (never through messaging: Firefox loses the user-action status there, Chromium after the first `await`), the background tracks `permissions.onAdded` and `permissions.onRemoved` — `usePermission`, and `permissions:request` kept only for the background's own entry points.
- **Entry points:** the toolbar action opening the popup; `background/menus.ts` with the context-menu entries from the plan, routed to surfaces or feature messages with their data validated; `background/commands.ts` from `shared/shortcuts.ts`; `background/tabs.ts` opening `https:` URLs on a user action and the full-tab page at a validated route, and opening the side panel from the background's own entry points only (a surface opens it itself, in its click handler, through the guard in `lib/`); `background/notifications.ts` with click-to-route; the omnibox keyword where the plan has one.
- **Alarms:** `background/alarms.ts` with the version check on startup and on an alarm a few times a day, and cache housekeeping.
- **Version and updates:** `background/version.ts` calling the backend's minimum-version endpoint (a configured path until the api-docs name it) with the platform and version headers, holding the state in `storage.session`; `runtime.onUpdateAvailable` applying the update when no surface is open.
- **Sign-in providers** the plan chose: the identity flow against the backend's native sign-in endpoints, and the email-and-password form's gateway calls.

## Step 7 — Test harness

- Vitest with WXT's plugin and the `surfaces`, `background` and `content` projects, `@webext-core/fake-browser` reset between tests, `renderWithProviders` with the messaging double, the gateway's MSW setup (`msw/node`) from the shared handlers with `onUnhandledRequest: 'error'`, and `src/test/fixtures/` with the example fixture page.
- Playwright configured against the `chrome-mv3` build: a persistent Chromium context with `--load-extension`, headless through the `chromium` channel (no display server needed), a fresh `userDataDir` per run, helpers to find the extension id and open a surface, a web server for `e2e/fixtures/`, and the smoke project (3–5 specs, tagged) and the full project.
- `e2e/README.md` listing the journeys and why each is there; the smoke suite starts with "the popup opens, paints the shell within the budget, and sign-in renders".
- One working test of each kind against the foundation: a unit test of a formatter and one of a message handler's validation and sender checks, a session test across a simulated worker restart, the gateway's refresh test against MSW, a surface integration test of the example popup screen, a content test of the example content script on its fixture, a manifest assertion test (permissions, CSP, ids per environment), and the smoke spec on the built extension.

## Step 8 — Observability and analytics

- Sentry per `security`: `@sentry/browser` in every context with the context name and the manifest version, initialised on Firefox only while the `technicalAndInteraction` data-collection permission is granted (feature-detected through `permissions.getAll().data_collection`) and stopped on `permissions.onRemoved`, scrubbing (page URLs reduced to the registrable domain in content scripts), source maps uploaded at build time, environment per build, the error boundaries reporting, expected `ApiError`s and offline failures filtered.
- `logger.ts` in every context with the scrubbing and levels `security` says.
- Where `analytics` is installed: the PostHog provider in each surface with the `connect-src` entry, screen tracking from the routers, identify and reset wired to the session events, the queue in `storage.session`, Firefox's `technicalAndInteraction` declaration, and `docs/analytics-events.md` started.

## Step 9 — Pipelines

- **The three GitHub Actions workflows `ci-cd` defines:** PR checks (three type-check projects, lint, tests, every target built with the manifest assertion script, `web-ext lint`, the `e2e` label path), the staging deploy with the staging builds, the unlisted Firefox signing with the sources zip, the artifacts, the `staging-current` tag, the Playwright run and the source-map upload, the `hotfix/*` triggers, and the production deploy with its release-owner check, SHA-only `commit` input, version check against the last `v*` tag, the smoke run, the `wxt submit` step per store with the sources zip for Firefox, the source-map upload and the `v*` tag.
- **The manifest assertion script** `ci-cd` names, reading each built manifest and comparing permissions, hosts, CSP, ids and `data_collection_permissions` against the environment's expectations.
- **Dependabot or Renovate** configuration, and the security policies `security` → Updates and supply chain requires. Check WXT's and `wxt submit`'s current documentation for the zip and submit options; they change.

## Step 10 — Docs sync with the backend

- `scripts/docs-sync.mjs` with `pnpm docs:pull` and `pnpm docs:push`, reading the backend repo path from `CLAUDE.md` and keeping, per synced file, the hash of the version last pulled:
  - **pull** copies from the backend every doc `documentation-conventions` lists as arriving from it, plus the backend's `docs/screen-specs/` and phase screen-spec files where they exist, and `docs/integration-handoff/` where it exists, replacing this repo's copies, and reports what changed. A file an earlier pull brought that no longer exists in the backend is deleted here and reported — the backend's promotion deletes a feature's phase folder, and the canonical files are then the specs. It refuses to overwrite or delete a file with uncommitted local changes, and never replaces a committed screen-spec draft that was never pushed. **This client's handoff files are the one exception to replacing:** they are three-way merged against the last-pulled version, so entries committed here and resolutions appended there both survive — both sides only append, so the merge never conflicts, and a real conflict stops with a message.
  - **push `--specs {file}`** copies one screen-spec file (a canonical area file, or a phase feature's file) to the same path in the backend's `docs/`; **push `--handoff`** copies `backend-issues-extension.md` and `backend-issues-extension-resolved.md` and nothing else. Both first check that the backend's copy is the version this repo last pulled, and stop with a message to pull first if it is not, so a stale copy never overwrites the backend's edits. Push copies nothing else, and refuses to copy a file with uncommitted changes, so what the backend receives is always a committed version.
- The `docs/` folders from the documentation map, with `.gitkeep` files where nothing exists yet. `docs/feature-areas.md` is never created here; it arrives from the backend.

## Step 11 — Infra guide

Write `docs/infra/infra-setup.md`: every step only I can do, numbered, so staging and production can be set up start to finish by following it.

- **Store accounts:** the Chrome Web Store developer account (its one-time fee, two-factor authentication, the publisher name as the listing will show it, and the publication limit — two items by default, so staging is never a store item), the Firefox Add-ons account and its API key and secret (used for the unlisted staging signing and the listed production submission), the Edge Partner Center account and its API credentials, and the Apple Developer Program where Safari is on.
- **Identities:** the generated `key` for the dev and staging Chromium builds and the ids it produces, the dev and staging `gecko.id`s, the production `gecko.id` you choose, and — once the first upload to each store assigns them — the production Chrome Web Store id (with the public `key` from its Package tab) and the production Edge Add-ons id (Edge ignores a `key` and assigns its own); the identity redirect URL each id produces per browser, and on Safari the `https` return page on the product's web domain.
- **With the backend:** register each redirect URL with the backend per environment, and confirm the backend contract from `security`, item by item, before the first integration — the platform header and tokens in the body, the native sign-in flow with an https redirect, the minimum-version endpoint per browser and the store listing it points to, account deletion.
- **On GitHub:** branch protection with PR checks required, squash merges, the release owners (whose usernames go into the production workflow), the `staging` environment with the Firefox credentials and the `production` environment with every store's credentials and the Sentry token, deploying only from `main` and `hotfix/*`; secret scanning with push protection.
- **Elsewhere:** the Sentry project per environment, the privacy policy and support pages on the product's web domain (both stores require them to resolve), the stock photo API keys and the image generation account if `/extension-build` will use them, and the analytics projects where installed.

Then **offer to walk me through it live.** Once the accounts and ids exist, record the ids, the dev and test commands, the E2E command and the sync commands in `CLAUDE.md`.

## Step 12 — Verify and report

1. **Verify from a clean clone:** install; `pnpm dev` in mock mode loads the dev extension into a fresh Chromium profile and the popup renders the example screen with mock data; the guard shows the signed-out state before sign-in; the mock sign-in stores the tokens and `useMe` resolves; closing and reopening the popup restores the session and paints from the persisted cache; a browser restart restores the session through the refresh path; the side panel and the full-tab page open at a route from the context-menu entry; the example content UI mounts once on the fixture page and unmounts on reload of the extension; `pnpm dev -b firefox` loads the same in Firefox; lint, the three type checks, unit and integration pass; `wxt build` succeeds for every target and the manifest assertion passes; `web-ext lint` passes on the Firefox build; each content-script bundle and the package are under budget; the smoke suite passes on the built extension; opening and closing the side panel ten times and reloading the fixture page ten times leaks nothing.
2. **Verify mock mode's edges:** a path with no handler is forwarded to the configured API URL with the `Authorization` header and without cookies; a build with `APP_ENV=production` ignores the mode and the test proves it; a message from a content script to a surface-only handler is refused.
3. **Report:** what was created, the commands, what remains for me (the infra guide), and any open decisions. The checks that need the store accounts — the unlisted Firefox signing, the identity flow against a registered redirect URL, a `wxt submit --dry-run` — run once the infra guide's store and backend sections are done; until then list them as pending.
4. **Deliver it as a PR.** Create a branch off `origin/main`, push to it, and give me the link to create the PR. Never create the PR yourself. The PR checks workflow added here runs on that PR. Say plainly that the PR is merged only after the infra guide's GitHub and Firefox-credential sections are done: until then the staging workflow fails at its signing step.
